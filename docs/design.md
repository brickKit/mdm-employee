# mdm/employee 的设计

本页写这个组件为什么这样设计：术语、拥有的数据、状态与规则、命令与事件、安全来源、实现状态与未决问题。写给要修改它的人与 AI。怎样使用、部署与配置在 `BRICKKIT.md`；代码在哪、怎样构建与测试在 `AGENTS.md`；跨组件的规则在装配项目的协议 02（投影与水位来源）、协议 07（生命周期）、协议 14（时间与业务日期、列表）、协议 15（安全来源的意图证据），安全 02（可信身份与属性）、安全 04（任职与授予）、安全 08（受保护操作）。

## 边界

拥有员工与任职：员工的标识、工号与在职状态，员工在法人、部门、岗位上的任职，账号与员工的关联。组织结构（法人、部门、岗位）归 `mdm/org`，账号与登录归身份组件，授予归 `infra/authz`（D06）。薪资、合同、考勤不并入，也不扩张成通用的人员库。

| 不在这里 | 归谁 |
| --- | --- |
| 法人、部门、岗位 | `mdm/org` |
| 账号、登录、第二因素 | 身份组件（`infra/iam-*`） |
| 授予、角色、确认记录 | `infra/authz`（账号关联的确认由它的受保护操作保存，安全 08） |
| 员工作为收款对象 | `mdm/partner` 的员工往来角色（D69，本版不做） |
| 待办的重新分配 | `infra/workflow`（消费任职结束，协议 09） |

## 术语

| 业务叫法 | 定义 | 代码标识符 |
| --- | --- | --- |
| 员工 | 一个自然人在一个法人的雇佣身份；工号在法人内唯一 | `employee` |
| 在职状态 | 预入职、在职、离职（见状态表） | `state` |
| 任职 | 员工在一个法人、部门、岗位上的一段任职，带开始与结束的业务日期；是**不可复用的资格实例**：结束之后再任同一岗位是新的实例（安全 04） | `appointment` |
| 任职的结束原因 | 调岗、离职、岗位退役、到期、手工结束 | `end_reason` |
| 账号关联 | 一个身份组件的账号（主体）关联到一个员工；一个员工可以有几个账号，一个账号至多关联一个员工；建立与结束都是受保护操作（安全 08） | `account_link` |
| 受限的个人资料 | 出生日期、证件号码：只给被授予可读字段的人（安全 09a 的受限字段） | `personal` |

## 拥有的数据

| 表 | 内容 | 终态与保留 |
| --- | --- | --- |
| `employee` | 员工：法人、工号、姓名与译名、在职状态、入职日期、离职日期、受限的个人资料 | `terminated`；不删除（擦除随数据生命周期统一，协议 03 的未决项） |
| `appointment` | 任职实例：员工、法人、部门、岗位、开始日期、结束日期、状态、结束原因 | `ended`；不删除 |
| `account_link` | 账号关联：员工、账号主体、状态、确认记录的身份、建立与结束的时刻 | `ended`；不删除 |

每条记录带版本，每次变化在同一个事务里以完整状态事件发布。日期是法人的业务日期（协议 14，按法人的时区，从 `mdm/org` 的投影取得）。

## 状态与规则

员工（协议 07 的生命周期）：

| 当前状态 | 命令 | 结果 |
| --- | --- | --- |
| （无） | 入职，入职日期在今天之后 | `pre_hire` |
| （无）、`pre_hire` | 入职日期到了（作业），或入职日期是今天及以前 | `active` |
| `pre_hire` | 取消入职 | `terminated`（`termination_date` 为空，原因 `cancelled`） |
| `active` | 离职，生效日期是今天及以前 | `terminated`；全部任职以 `termination` 结束 |
| `active` | 离职，生效日期在之后 | 仍是 `active`，记下 `termination_date`；到期由作业办理，到期前可以撤回 |

任职：

| 当前状态 | 命令 | 结果 |
| --- | --- | --- |
| （无） | 任命，开始日期在之后 | `planned` |
| （无）、`planned` | 开始日期到了，或开始日期是今天及以前 | `active` |
| `planned`、`active` | 结束（手工、调岗、离职、岗位退役），或结束日期到了 | `ended` |

不变量：

- 任命时员工不是 `terminated`，部门与岗位启用，岗位属于这个部门、部门属于这个法人（按 `mdm/org` 的投影；投影缺这条记录或不够新时拒绝，不猜）。
- 同一员工在同一岗位上的任职有效期不重叠（按日期区间，结束日期为空视为无限）。
- 调岗不改原任职：结束原任职（原因 `transfer`，最后一天是调岗日期的前一天），新建任职，一次办理；法人、部门、岗位都是有安全含义的字段，不原地改（安全 04）。任职的显示类字段（备注）可以原地改。调岗的日期不晚于今天；将来的调岗是给原任职写结束日期（到期以“到期”结束）、再任命一条计划中的新任职。
- 离职生效后全部任职结束；之后不能再任命或建立账号关联。已有的账号关联不随离职结束：关联是“这个账号是这个人”的事实，员工的状态说明人已离开；账号是否停用由身份组件的生命周期政策决定（安全 04、安全 02）。
- 岗位退役（`mdm/org` 的事件）时，挂在它上面的未结束任职以 `position_retired` 结束；部门退役同样（原因 `unit_retired`）。主数据不读下游：`mdm/org` 不查任职，由本组件消费它的事件。
- 一个账号至多一条未结束的关联；关联只由人经受保护操作建立，不按姓名、邮箱、工号自动匹配（安全 02）。
- 一份确认只用一次：关联的建立与结束各记下用到的确认，在本组件里唯一（授权组件应用之前，同一份确认在那边还核对得过）。

**账号关联是受保护操作**（安全 08 第 21 行）：建立与结束都要一份确认。

1. 管理者在授权组件建立确认（对象是“员工的账号关联”，绑定员工、账号、动作与员工的当前版本）；确认人要独立：不是申请人，不是这个员工本人的任何账号（同一员工的几个账号算一个人，读本组件的关联），且此刻是合格的管理者；没有别的可用管理者时由部署所有者确认（安全 08 的确认表）。
2. 管理者带着确认的身份调用本组件；本组件在事务之外经授权组件的系统面核对这份确认（`AccountService.CheckLinkChange`：存在、绑定一致、未使用、未过期，确认人合格），在事务里核对员工仍是确认绑定的版本，然后写关联，关联记录带着确认的身份。确认不在这里消耗：授权组件从本组件的水位流应用这条关联时把它标为已用（与身份组件的账号状态相同），所以同一份确认不能用第二次。
3. 没带确认或确认不符时答 `CONFIRMATION_REQUIRED`（202），不改任何东西。

**最后的授权管理员**（D62）：离职与结束账号关联照常办理；办理前问授权组件“这些账号里有没有授权管理员”（`AccountService.Administrators`，契约 `contract-infra-authz` alpha.6），有就在响应里带上提示（`last_admin_warning`），不阻止。可用的授权管理员变成零时由授权组件让部署进入待恢复（安全 08）。

**安全来源**：本组件是员工、任职与账号关联的**水位来源**（协议 02），授权组件按水位判断“任职结束”“账号属于哪个人”是否足够新。收紧性的变化先在事务外写意图证据，再提交（协议 15，照 `mdm/org` 的做法）：

- 记什么：离职（`termination`），任职结束（`appointment_end`），账号关联结束（`link_end`）。类别都是 `employee_tightening`；对象是员工（`mdm.employee.employee`）、任职（`mdm.employee.appointment`）或关联（`mdm.employee.account_link`），带变更前的版本。
- 不记：入职、任命、建立关联：这些不收紧任何人的访问，恢复时丢了只会少给。建立关联本身有授权组件保存的确认记录。
- 作业到期办理的离职与任职结束也先写意图（执行者是作业）。
- 整套恢复后按证据重新办理（重放）：只查对象还在，不重做业务前置校验。

其余：发件行在锁内按提交后编号，发布位置带纪元，事件只含可投影字段，受限的个人资料不进事件；高可用部署中全部写入同步提交（D66）。

## 命令与查询

| 命令或查询 | 用户面或系统面 | 权限键 |
| --- | --- | --- |
| 入职、取消入职、修改员工资料、离职（含撤回未到期的离职） | 用户面 | `mdm.employee.manage` |
| 读取与列出员工（按法人、状态、关键字）；受限的个人资料按可读字段遮蔽 | 用户面 | `mdm.employee.read` |
| 任命、结束任职、调岗（一次办理：结束原任职并新建）；某人的任职、某岗位的持有人 | 用户面 | `mdm.employee.appointment.manage`（读取 `mdm.employee.appointment.read`） |
| 建立与结束账号关联（受保护，带确认）；某员工的账号、某账号的员工 | 用户面 | `mdm.employee.account_link.manage`（读取 `mdm.employee.account_link.read`） |
| 来源方法：水位补取与记录读取（三种记录） | 系统面 | `mdm.employee.system.read`；补取只给声明的补取者（`infra/authz`） |
| 补发、恢复核对、证据重放 | 系统面 | `mdm.employee.system.resend`、`.recover`、`.replay` |

任职维护权不等于授予权（D30）：`appointment.manage` 只改人事事实，授予由 `infra/authz` 的管理者办理。

## 事件

流 `mdm.employee`（4 个分区，水位来源，带记录读取）：`mdm.employee.changed.v1`、`mdm.employee.appointment.changed.v1`、`mdm.employee.account_link.changed.v1`，都是完整状态（受限字段除外）。任职的开始与结束就是任职事件里状态的变化。

消费：`mdm/org` 的 `mdm.org_unit.changed.v1`、`mdm.org_position.changed.v1`、`mdm.legal_entity.changed.v1`（投影：任命时核对，退役时结束任职，业务日期按法人时区）。

## 依赖

`mdm/org`（必需：投影与事件）；身份、授权（必需：账号关联的确认核对、最后管理员的提示）；`infra/audit`（可选，兼任证据存储：缺时收紧的意图走外部告警渠道，协议 15）。

## 数据范围

任职按法人（`legal_entity`）与所在部门的路径（`department`，组织树维度，安全 07）限定；员工与账号关联只按法人限定。

## 实现状态

首批（装配项目阶段计划 C1，`dev` 区的 `c1-employee-plan.md` 的 E0）做上面的全部，以下不在首批，契约里有、调用答“能力不支持”（`CAPABILITY_UNSUPPORTED`，D75）：

| 能力 | 什么时候做 |
| --- | --- |
| 员工往来角色的开通与暂停（D69） | 第一个报销或薪资组件开工 |
| 入职事件驱动身份组件自动开通账号 | 客户要求自动开通（本组件照常发事件，消费在身份组件） |
| 导入与期初任职（协议 16） | 第一次上线迁移 |
| 本人资料变更申请 | 员工自助开工 |

授权组件一侧的任职关联授予只做“任职结束时撤销绑定它的授予”；新任职的授予建议（D30 的后一半）随后做。

## 部署与替换

读多写少，适合外壳。同契约的实现可以接替；与外部 HR 系统同步时以适配器写入。适用协议 02、07、08、13、16，安全 02、04、08。

## 验证故事

| 故事 | 本版 |
| --- | --- |
| 审批人离职，待处理任务按岗位转给接任者 | 任职结束事件已发；转交由 `infra/workflow`（C7） |
| 调岗后旧任职关联的授予自动撤销，新授予待确认（D30） | 撤销由授权组件（C1 的 E4）；新授予的建议随后 |
| 一人两个账号映射到同一员工，职责分离按人检查 | 关联与水位已做；按人检查由授权组件的确认与审批（协议 09） |
| 岗位退役，挂在上面的任职结束 | 消费 `mdm/org` 的事件 |

## 未决问题

- 未来日期的入职、离职与任职由一个单例作业每分钟办理到期的：按法人的业务日期（午夜在不同时区），到期后最晚一分钟生效；更细的时点要求出现再改。
- 受限的个人资料的擦除：随数据生命周期统一（协议 03 的未决项）。
- 员工按部门限定：一个员工兼任时有几条部门路径，SDK 的组织树维度一行只取一条路径（`列 = 路径` 或前缀）；要按部门限定员工，要么 SDK 支持多值的组织树列，要么引入“主任职”。首批员工与账号关联只按法人限定，部门级的人事管理员看得到本法人的全部员工（看不到别的法人的）；第一个要求按部门隔离员工的客户出现时定。
